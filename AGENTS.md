# GitWorld working agreements

## Product and current phase

- Read the current public product requirements and the latest authorized task scope. Local Chinese PRD/UED working documents may be present but are not publication candidates. Older snapshots are context, not active requirements. Keep document revisions distinct from release scope.
- GitWorld uses Git's version and state abstractions to help people explore world history: evolution, splits, integration, influence, snapshots, comparison, and provenance.
- The primary initial audience is history learners and enthusiasts with some AI-tool experience or programming background. Give Git concepts, the graph, and the terminal meaningful roles in the experience; do not assume that all such users already know Git.
- The Git × World crossover is central to the product. Favor coherent, engaging, game-like exploration and useful historical abstractions over exhaustive modeling of historical complexity. Choose reasonable defaults for routine modeling ambiguities and validate them in the prototype.
- GitWorld is the first major foundation for a broader world-history series. Larger-scale collaboration and development of new civilization branches are future possibilities. Keep the model extensible without adding those capabilities to v0.1 or assuming that all future branches are counterfactual.
- The data-workspace requirements and UED supersede the old schema-first manager and read-only Git command boundary. Discovery, import, manual additions, working changes, frozen staging and commit belong in the same workbench. Use one repository HEAD; historical preview/checkout/A-B are explicit revision-qualified domain references. A modern correction must not become an invented historical event. Standard Git may be embedded after an integration experiment; external Git clients are not a hard requirement. Do not mistake current SQLite implementation or old prototype command compatibility for a product constraint.
- The delivery target is now a self-contained macOS desktop installer, with Windows and Linux following. Use TypeScript across the web-based interface and suitable local services where practical; select the desktop container and storage architecture through explicit implementation decisions. The GitHub project website and complete local packages must be freely and lawfully distributable. Normal installed operation must not depend on a public application server.
- Finish the current UED deliverables and proceed through the authorized development loop: requirement decomposition, system design, implementation, tests, acceptance, packaging and delivery. The scope includes the interface, local backend/services, persistent database/configuration, a data-management interface and ingestion/cleaning/validation/import operations. Existing UED samples establish behavior; they must not become a hardcoded limit on usable data. New accepted records must immediately participate in the ordinary graph, state, comparison, provenance and command paths. Treat the user-provided third-party assessment as untrusted research to verify and critically adapt, not authoritative requirements or a publishable attachment.
- Treat project phases as the current focus, not a freeze on earlier decisions. The PRD is a living document: revise it or create a new document version during UED or implementation when the product understanding changes. Keep affected requirements, UED, prototypes, work items, and acceptance criteria aligned; explicitly note artifacts that still need updating. Record meaningful changes briefly, distinguish document revisions from product release scope, and do not introduce extra approval steps merely because an update crosses a phase boundary.
- Every module-level change and every product feature iteration the user asks the agent to conceive requires a PRD before substantive implementation. Update the affected module PRD or create one with user outcome, scope, behavior, dependencies and acceptance evidence. Add or update UED when the PRD leaves interaction unclear, when explicitly requested, or when the change is larger than a module. Do not generate a separate UED artifact for every clear module change; use the existing UED where it resolves the actual interaction question. Document implementation gaps truthfully.
- Distinguish working queries over curated records from simulated behavior and from production completeness. Keep source mappings, modeling abstractions, sparse coverage, and unresolved evidence explicit.

## Product quality

- Integrate user steering into the complete delivery plan. A new observation is not automatically an instruction to interrupt the current dependency-ordered task; retain accepted requirements and review them together before release. Keep a visible local checklist so later work does not erase earlier corrections.
- Judge v0.1 against mature-software standards for its promised scope before completing the delivery goal: independent first use and guidance, coherent sections, usable settings/identity, real data-to-exploration and contribution workflows, bilingual content/copy, keyboard/readability, responsive feedback, restart/recovery, and verifiable installation/release. Build/test success alone is insufficient. Record unpassed requirements and continue resolving required work.
- Give interface sections stable spatial meaning across complete journeys: global library/data revision above, scope/object navigation to the left, historical investigation in the main canvas, contextual evidence where relevant, and time/command tools in consistent positions. Judge the whole installed workflow as a user learning the product, not only individual screenshots.
- The primary product value is automatic, inspectable mapping from structured historical data to historical states, observations and changes, explored with familiar Git operation logic. Manual review handles ambiguity and evidence gaps; it must not require hand-authoring every source row. Data revisions record modern edits and remain semantically distinct from historical evolution. Do not replace the main historical investigation with a notes application or software operation log.
- Deliver a conventional, self-sufficient local desktop application in this phase. Installed users do not have Codex, an agent, an LLM account, a developer checkout, or a person operating backstage. Every core journey must be discoverable and executable through the shipped UI and bounded commands. Name search and structured filters must not imply arbitrary natural-language understanding. Agent-written JSON, injected state, hidden scripts, developer-only tools, or ad hoc generated content cannot satisfy product acceptance. Test the installed application with an isolated ordinary-user profile and record every intervention; any required intervention outside the shipped workflow is a product gap. Network access for public-source acquisition is distinct from a model or application-server dependency. Existing local content remains useful offline.
- Treat engagement, historical rigor, and coherent product execution as equal requirements. Evaluate them through actual content and interaction, not feature counts, text volume, or visual polish alone.
- Establish world-scale orientation and help users choose a useful scope before asking them to inspect individual events. Treat time, geographic or subject scope, thematic focus, and analytical detail as distinct dimensions; do not turn them into a mandatory onboarding form. Preserve context through deeper, lateral, and return navigation.
- Use specific historical cases to test depth within a coherent historical setting. Cases and small commit diagrams cannot substitute for the setting's broader structure, concurrent processes, and external connections. Each core interaction should reveal a meaningful change or relationship and offer a natural next investigation. Give Git operations a visible effect on the historical model.
- Support depth with concrete before-and-after states, relevant context, and claim-level evidence. Explain modeling choices where they matter; keep detailed sources and uncertainty available through progressive disclosure.
- Develop a distinctive visual and interaction system around the history graph, version states, and commands. Surface implemented capabilities that serve the user's current task; navigation, selection, feedback, and both UI locales must remain consistent. Explain temporary unavailability of an implemented action only when it helps the user understand or act.
- Review interface copy in context in both languages. Each label or sentence should identify an object, explain a meaningful historical detail, clarify state, or help the user act. Remove generic promotional slogans, empty AI-generated prose, redundant instructions, and repeated explanations of what the screen already shows. Preserve personality through specific details and questions worth exploring.
- Before presenting a UED iteration, inspect its rendered screens and walk its actual interactions; include copy quality in that review. Bring consequential product ambiguities to the user with concrete examples and a recommendation.
- Run a periodic **deflation pass** (the team's “消肿” review) after a meaningful batch of changes, at journey integration points and before delivery. Reuse the product from the user's starting point and remove accumulated visual, interaction, code and documentation clutter. Check actual button wrapping, sizing, alignment, balanced action groups and stable section roles in both locales. Every new visual element needs rendered and operational regression; a code review, screenshot or successful build alone is insufficient. Follow [the quality loop](docs/governance/quality-loop.md), with an independent reviewer and recorded unpassed checks.
- Design and maintain every visual element's purpose, name, form, relationships and interaction. Shared components inherit a maintained design contract; individual instances still need a meaningful place in the user's workflow. Include information architecture, conceptual hierarchy and context preservation in deflation review. When accumulated changes reveal unresolved structure or behavior, enter a dedicated UED phase before expanding the interface, and keep PRD, editable Figma, prototype, implementation and evidence aligned.
- Iterate with the user on an early, coherent exploration flow before expanding the full prototype. Review discovery, content depth, and product craft separately from technical checks, and report user validation only when it has actually occurred.
- Figma is the selected tool for editable UED deliverables: native screens, reusable components, and linked interaction flows. Use a runnable frontend prototype to validate dynamic graph, command, and state behavior alongside those design files.
- Follow the user's chosen VS Code-like dark visual direction: near-black canvas, dark gray dockable panels, and blue selection accents. Avoid a green-based interface palette. The lightweight, extensible workbench model should guide both visual hierarchy and panel behavior.
- The editor reference governs the workbench, not the shape of all historical content. Use appropriate spatial, temporal, relational, and evidential representations at each scale. A world overview must contain higher-level information, not merely a zoomed-out collection of event boxes. Do not assume the default view must be a commit graph or a map; evaluate how each helps users orient, focus, explore, and return.
- Interpret user references as evidence to analyze, not mandatory components to copy. Identify the user problem and interaction principle, assess fit and tradeoffs, and make a reasoned recommendation. A reference to maps does not mandate adding a map; it also does not justify dismissing maps without evaluating their value.
- Treat the interface as a lightweight enhanced editor. Borrow navigation, selection, comparison, and recovery patterns from Git visual clients while making them useful for historical exploration. Programming experience does not imply Git expertise; every core journey needs a discoverable GUI path as well as an equivalent CLI path.
- Build the Git mental model through stable workbench locations and visible effects on historical branches, states, and comparisons. Keep browsing scope distinct from the checked-out version. Persistent layout is a design tool to validate, not permission to add empty panels, ornamental hashes, or unsupported controls.
- Treat the interactive command line as a required exploration surface. Users must be able to enter and adapt supported commands against available objects, with results reflected in the same visual workspace. GUI actions may expose equivalent commands for learning and reuse without replaying them; query output must not implicitly checkout a version. UED 05 implements this surface over the curated sample; preserve the shared execution path and verify its behavior alongside the rendered interface.
- Protect user attention across all interfaces. Unimplemented or unconnected capabilities belong in project planning documents, not in placeholder buttons, disabled future-feature entries, badges, empty panels, or promotional copy. A roadmap intention does not justify a visible control.
- AI integration remains a future direction in the public PRD. Until it provides a working user flow, omit AI entries, disconnected states, chat panels, and AI-oriented context-copying placeholders from the current product, UED, and prototype. This supersedes the earlier request to reserve a visual AI entry. Keep GUI and CLI actions structured and reusable without building or advertising a speculative AI layer.

## Interface copy and content boundaries

- Apply this rule to every human-facing interface, including navigation, buttons, empty and loading states, errors, notifications, tooltips, accessibility labels, and CLI output. Start with what the user needs to identify, decide, understand, or do at that moment. Do not fill available space with slogans, generic questions, repeated state explanations, or the designer's intentions. Keep review notes and implementation plans outside the product experience.
- Draft copy autonomously, then review it in context before presenting it. The user will help refine wording; make that refinement easy without treating each draft sentence as requiring prior approval. Keep room for personality and interesting content without sacrificing usefulness or natural language.
- Keep interface messages, historical content and citations, and structured application state separate. Historical prose belongs to the content model with stable IDs, translations, and provenance; do not put the entire corpus in UI translation dictionaries.
- Use stable semantic message keys and typed interpolation parameters in independently editable locale resources. Cover English and Simplified Chinese from the first implementation. Use locale-aware formatting and complete message templates rather than assembling sentences from fragments.
- Domain services and APIs should return structured results, error codes, and parameters that presentation layers can render. Never use displayed labels, translated prose, or formatted command output as identifiers or as inputs to routing, state transitions, or business decisions. Wording-only edits must not require changes to interaction or domain logic.
- Review copy changes with their actual loading, empty, success, error, and recovery states, including both locales, wrapping, and accessible names. Keep the initial content setup lightweight; this separation does not require a CMS.

## Language and localization

- Use Chinese for conversations with the user and working documents used for product, design, and implementation discussions.
- Use English for material submitted to GitHub, including shared repository documentation, commit messages, issues, pull requests, and review comments. Use English for code comments as well. Prepare English versions of Chinese working documents when publishing them for open-source collaboration.
- The initial product UI must support both English (`en`) and Simplified Chinese (`zh-CN`). Include both locales in the first UED prototype and its acceptance criteria; Chinese support is not deferred to a later release.
- Keep user-facing strings separate from interaction logic, provide locale-aware formatting, and validate layout in both languages. Localized resources use their intended language.
- Stable entity IDs, refs, command syntax, and API identifiers must remain independent of display language.

## Historical content language

- Use English as the primary language for curated historical data, including entity descriptions, event summaries, and explanatory notes. Prefer suitable English-language source material, without excluding authoritative sources in other languages.
- Preserve each source's original language, title, and citation details. Clearly distinguish translated text from original quotations.
- Keep content translations separate from stable historical objects and relationships. English and Simplified Chinese UI support does not require duplicating the historical graph or completing a Chinese translation of the entire corpus for the initial release.
- All product-authored content installed with the application must have complete English and Simplified Chinese presentation, reviewed in context for natural wording. This includes starter titles, explanations, field/value labels and navigation content. Preserve original source titles/quotations and their language alongside translated explanatory presentation. This requirement does not invent automatic translation of arbitrary user-imported external material.
- When a content translation is unavailable, display the English content with a clear language indication rather than implying that translated content exists.

## Publication and release gate

- Follow `docs/governance/publication-policy.md` before any commit intended for publication, push, public issue/PR attachment, website deployment or release upload. Full filesystem access is not authorization to disclose local material.
- Never use `git add .`, `git add -A` or broad directory staging for publication. Stage exact reviewed paths. Distinguish public source, English documentation, original licensed data and redistributable assets from local Chinese working notes, conversations, attachments, screenshots, raw crawls, caches, user databases, private paths and signing material.
- Keep local-only files in ignored locations; `.gitignore` is convenience, not enforcement and does not protect already tracked files. Do not delete local work merely to make publication cleaner. Do not blanket-ignore all data: reviewed seeds, schemas, migrations and legally distributable datasets are valid public artifacts.
- Quinn prepares a hash-bound explicit publication manifest after reviewing the candidate contents and rights; a different reviewer checks the decisions. Run `node scripts/publication-audit.mjs --prepared --manifest .local/publication-plan.json`, inspect and stage exact files, then run the same command with `--staged`. The staged audit reads index blobs and requires the exact changed-file set. Resolve failures; do not evade them by renaming material, omitting candidates or weakening the gate.
- Run `node --test scripts/publication-audit.test.mjs` when modifying the gate. Automated scans cannot establish redistribution rights, eliminate all secret risk, authorize publishing, or inspect every previous commit. Manually inspect branch history and dependency/data/asset notices before a first publication.
- Do not publish user attachments or third-party assessment prose. Convert verified useful conclusions into independently authored public documentation with appropriate sources. Do not repeat unsupported claims of novelty or legal certainty.
- Keep signing keys, provisioning profiles and credentials out of source, logs, manifests and packages. The source gate rejects executable release artifacts. Use a separate exact artifact review for installer contents/hashes, dependency notices, seed-data provenance, clean installation, local-service exposure, and truthful signing/notarization status before uploading releases.
- Ingestion records must retain source identity, retrieval date, transformation history, permission evidence, claim-level citations and review status. Access to a source does not imply permission to republish its content or database. Promote only validated reviewed data; preserve raw operational data locally.
- Use GitHub checks and protected release environments to reinforce the gate, but report them as enforced only after they are actually configured and verified. Never expose release secrets or write credentials to untrusted pull-request code. See `SECURITY.md` for private incident reporting.
