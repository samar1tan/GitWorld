# Product assessment: evidence, decisions, and open questions

Date: 25 October 2026. Scope: the first desktop development loop and historical data operations. This is a product assessment, not a claim of historical consensus, market exclusivity, or completed implementation.

## Decision

Build a local desktop history workbench with a usable content-management loop. The combination of historical states, ancestry, comparison, evidence, and adaptable commands is worth testing. Its value must be demonstrated through investigations that users can carry out, including investigations over newly entered data. A polished, permanently fixed sample does not satisfy that objective.

The initial distribution target is macOS. A local database and domain service support exploration, structured editing, validation, immutable publication, and recovery. Initial records bootstrap the library; they are not compiled into the only possible runtime dataset. Windows and Linux remain portability targets until their packages are built and tested. The complete acceptance contract is in [PRD v0.3](../PRD.md).

## Claims that need correction

| Claim | Assessment and evidence | Product consequence |
| --- | --- | --- |
| The workspace is a globally unprecedented invention | Not established. A bounded survey cannot prove that no comparable product exists. Legal version-control projects already apply Git to non-software history, while historical databases and atlases cover other parts of this problem. [France's civil-code repository](https://github.com/steeve/france.code-civil), [DC Council law XML](https://github.com/DCCouncil/law-xml) | Describe the actual combination and its intended benefit. Do not market it as the first or only system. |
| Programming or AI-tool experience makes Git interaction automatic | A hypothesis without user evidence. Familiarity with programming is not demonstrated mastery of refs, ancestry, checkout, or three-dot diff. | Provide discoverable GUI paths, contextual explanations, and reusable equivalent commands. Test understanding separately from command completion. |
| Existing historical products are merely colored maps or linear text | Too broad. Running Reality documents stateful objects, citations, uncertainty, editing and review. OpenHistoricalMap exposes reusable historical data and contributor workflows. [Running Reality factoids](https://runningreality.org/docs/reference/factoids.jsp), [editing](https://runningreality.net/docs/tutorial/editing.jsp), [OpenHistoricalMap](https://www.openhistoricalmap.org/about?locale=en-GB) | Learn from their source handling and content operations; investigate where field comparison adds value instead of dismissing their models. |
| 1648 cleanly separates overlapping authority from modern sovereign states worldwide | An unsuitable universal boundary. Osiander's research directly challenges the conventional Westphalian origin narrative. This does not make the treaties irrelevant; it prevents their use as a universal schema switch. [Osiander, 2001](https://www.cambridge.org/core/journals/international-organization/article/abs/sovereignty-international-relations-and-the-westphalian-myth/33B6B7773432BE494F31518952ABE881) | Give political relationships temporal and geographic scope. Do not assume uniform statehood, exclusive territory, or a global pre-/post-1648 ontology. |
| A Git commit is fundamentally a delta inherited from its parent | In native Git, the commit references a snapshot tree and parent objects. Computing a change set between snapshots is a separate operation. [Pro Git: Git Objects](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects) | GitWorld deliberately stores explicit changes and verifies replay against a snapshot hash. Explain this as a domain design, not a literal description of every Git object. |
| Native Git branches cannot exchange changes without merging their ancestry | Git's cherry-pick applies changes from existing commits without requiring a merge-parent relationship. This still does not supply a historical theory of cultural transmission. [git-cherry-pick](https://git-scm.com/docs/git-cherry-pick) | Keep sourced influence links explicit. A software operation can illustrate the distinction but cannot establish that historical borrowing occurred. |
| Git's epoch makes ancient history impossible to store in Git | The limitation concerns use of author/committer timestamps as historical dates. Git documents those timestamps as seconds since the Unix epoch. The civil-code project used a workaround, but that does not forbid separate historical-date metadata in a repository. [git-commit-tree](https://git-scm.com/docs/git-commit-tree), [civil-code technical note](https://github.com/steeve/france.code-civil) | Store historical time, including BCE and uncertainty, separately from modern editorial time, regardless of the object-store choice. Do not force ancient dates into Git metadata. |
| Slash-separated branch names require a virtual ref table | Git explicitly permits slash grouping. A prefix collision such as `francia` alongside `francia/west` is a narrower constraint, also covered by Git's own tests. `francia/main`, `francia/west`, and `francia/east` can coexist. [ref-name rules](https://git-scm.com/docs/git-check-ref-format), [Git ref error tests](https://github.com/git/git/blob/master/t/t1404-update-ref-errors.sh) | Use stable naming conventions. Choose SQLite for local transactions and content operations, not because hierarchical names categorically rule out Git. |
| An as-of result reconstructs the entire historical world at that year | Not from sparse records. A latest-record query only establishes which authored state the system returned. An observation of a value does not necessarily establish when it began. [Running Reality editing model](https://runningreality.net/docs/tutorial/editing.jsp) | Show requested and recorded dates, query boundaries, and inherited fields. Overlapping uncertain dates require an explicit result or ambiguity, not an invented midpoint. |
| A code chronicle proves deep cognitive equivalence between Git and civilization | `repo-saga` documents an interesting reverse metaphor: repository commits become evidence-backed eras and events. That is an example, not a cognition study. [repo-saga](https://github.com/teee32/repo-saga) | Borrow useful presentation ideas without treating an analogy as empirical validation. |
| More variables or a confidence label automatically produce rigor | Unsupported. Seshat distinguishes uncoded, inferred, uncertain and expert-unknown cases, with explicit coding conventions; these cannot be collapsed into one default certainty badge. Its legacy codebook also encodes some transition uncertainty in values rather than arbitrary uncertain-date syntax. [Seshat codebook](https://www.seshat-db.com/codebook), [methods](https://seshat-db.com/methods/) | Separate absence, missing entry, applicability, inference and disagreement. Do not label a sourced claim as scholarly consensus by default. |

Local reproducibility check: on Git **2.55.0**, an isolated temporary bare repository accepted `francia/main`, `francia/west`, and `francia/east`; adding their parent-prefix `francia` was rejected. `git commit-tree` rejected both a 1960 ISO author/committer date and the negative timestamp `-1 +0000`. This confirms the tested behaviors of that installation. It does not establish every Git version's supported date range or the impossibility of storing ancient dates as content.

## Competitive evidence and naming

The official [gitworld.live site](https://www.gitworld.live/) uses **GitWorld** for a product that renders GitHub repositories as an isometric city. This establishes a real naming collision and potential search confusion; it does not establish trademark ownership, applicable legal rights, or availability of any alternative domain. Keep the repository name for now and use the descriptive subtitle **World History Workspace**. No domain purchase, account registration, or rename follows automatically from this finding.

This was a bounded source review on the date above. No exhaustive competitor inventory, trademark clearance, market-demand study, or educational outcome experiment was completed. Search-index extracts were available for parts of Seshat's codebook where direct retrieval was blocked; its rules are treated as documented conventions, not as validation of our implementation. Specific EU4 script dates, blanket accounts of other projects' failure, and alleged historical-map errors were not reproduced against authoritative versioned artifacts. They are not used as evidence for our product decisions.

## Adopt, adapt, and decline

**Adopt:** separate parent and influence relations; retain sources at the field/relationship level; distinguish dataset baselines from historically evidenced transitions; make comparison, ancestry, and trace results work on arbitrary valid records; preserve bilingual interfaces and English-first historical content.

**Adapt:** shared field paths need definitions and applicability, not forced uniformity across societies. A court residence can be compared where it is meaningful; an unmodeled capital, a mobile court, and evidence that no singular capital existed must not become one null. Integration needs a field-resolution table identifying the contributing parent, a new sourced value, or an explicit unresolved result. A conquest must not be labeled a voluntary merger.

**Decline as the completed product:** static-only frontend data, a database seeded anew on every launch, a management page that only lists records, and content expansion that requires editing TypeScript and rebuilding. A structured JSON import remains useful, but it cannot replace usable forms for routine editing and source selection.

**Defer:** online multiuser accounts, simultaneous collaborative editing, counterfactual branch simulation, AI generation, global coverage, and public cloud deployment. These do not excuse missing local management, release history, backup, or restore in this development loop.

## Data loop and tradeoffs

The local loop is: **enter or import → validate → preview state and release diff → publish atomically → explore the new release → correct through another draft → export and restore**. Historical event time stays distinct from editorial modification time. A workspace pins a dataset release; publishing new data does not change its resolved comparison endpoints.

SQLite is the default local store because structured queries and transaction publication fit this loop. The choice is practical, not a claim that a native Git store is impossible. Atomic publication still requires implementation tests: database transaction guarantees do not automatically validate application code. [SQLite atomic commit](https://www.sqlite.org/atomiccommit.html)

Backups must be consistent snapshots with a tested restore path. Copying one live database file without handling its storage mode is not a sufficient backup design. Use a supported backup mechanism and verify recovered objects and releases. [SQLite backup documentation](https://www.sqlite.org/backup.html)

## Acceptance and unresolved evidence

| Question | Required evidence | Present conclusion |
| --- | --- | --- |
| Is it more than a fixed demonstration? | Add a new sourced subject/version through management, publish, restart, and explore it without a build. | Required; the old sample does not prove it. |
| Can corrections be trusted? | Reopen a pinned old release after a correction; verify its state, source metadata, and comparison remain unchanged. | Required. |
| Does the full model work? | Sourced split, multi-parent integration, separate influence relation, BCE/uncertain time and complete command contract. | Existing single-parent examples are insufficient for the complete claim. |
| Is the desktop artifact usable? | Launch the packaged app without a developer server, persist changes, and recover a backup on the declared macOS/architecture. | Report actual package tests and signing/notarization state separately. |
| Does Git improve understanding? | Target users explain a continuity, a difference and the meaning of inherited/missing data, then pursue an unprompted query. | Unverified until observed. |
| Is it fast at useful scale? | Measured cold start and query latency on documented hardware and a specified dataset, with synthetic stress data kept separate. | No blanket millisecond claim. |
| Is the brand clear and available? | Searchability evaluation and, if public-launch decisions require it, appropriate name-rights review. | The same-name site is verified; exclusivity and clearance are not. |

The acceptance matrix in [PRD §11](../PRD.md#11-acceptance-matrix) is the completion contract. Passing code checks, viewing a screenshot, testing a desktop package, verifying historical claims, and observing user comprehension are distinct forms of evidence.
