# Complete local library backups

A current GitWorld backup is a `.gitworld` file containing the complete local library. It includes historical releases and workspace data in SQLite, adopted objects and assertions, research records, source archives and acquisition checkpoints, plus the Git working files, frozen index, commits, refs and retry receipts. It does not require an installed Git, developer checkout or model service to restore.

Paired collection imports also retain their immutable preview, prepared/completed import receipt, versioned vocabulary sources/references and any pinned legacy display catalog. A pending import survives restart and complete restoration with the same input and generated identities. Its retry must not overwrite a later working edit. These optional stores and current vocabulary references are validated in the candidate directory before replacement. A malformed candidate preserves the original library. An older backup without catalog bytes remains readable, but cannot reproduce metadata that was never stored; its compatibility fallback is explicitly identified rather than presented as part of an old Git commit.

The pending-import summary and resume operation remain available after restoration. Resume uses the stored operation and preview identifiers, without the previous file token, source access or renderer memory. It neither changes the accepted review choice nor registers a second import.

Navigation contexts and memberships are versioned metadata in the same Git tree. Complete backups retain their committed, staged and working versions, plus the optional `navigation.sqlite` immutable plans and prepared/completed operation receipts. Definition or membership recovery resumes its own operation; it does not replay an import or approve historical claims. Older libraries without this metadata remain unclassified.

An interrupted classification may have made only some membership shards durable. Candidate validation checks each participating file against its recorded baseline or prepared bytes, then validates the completed overlay and the frozen staged metadata, including object/definition/source references. Unknown schemas, unexpected partial bytes or a dangling completed overlay reject before directory exchange. Until its receipt is resolved, scope/context queries return the structured `navigation-operation-pending` requirement rather than partial statistics. Pending summaries, original plan review and explicit object history remain available; the backup keeps enough state to resume without the original renderer input. This extends candidate validation without changing the backup container, admission, cancellation or directory-exchange protocol.

Finish or cancel active source acquisition before starting backup or restore. The service blocks concurrent requests while it snapshots or replaces the library, including source-list operations that maintain local caches. A coherent SQLite snapshot includes committed WAL contents; the backup does not copy a live database file alone.

The container has a versioned magic header, a compressed file manifest and streamed file contents. Every entry records its size and SHA-256. Import rejects traversal, absolute or backslash paths, duplicate and case-colliding entries, source symlinks/hardlinks, invalid hashes, invalid SQLite data and unexpected trailing decompressed contents. Current limits are 100,000 files, 8 GiB uncompressed total, 2 GiB per file and a 64 MiB manifest. These are format safety bounds, not measured performance claims.

Restore validates the complete candidate before closing live stores. It installs through a directory exchange and reopens the service. A failed reopen returns to the previous complete library. Previous and failed candidate directories remain local for recovery. A durable journal also handles interruption: startup rolls back an unfinished exchange, while a completed exchange retains the restored library. These guarantees have process-termination tests; they are not a claim about every filesystem or power-loss scenario.

Staged and unstaged work remain distinct after restore. For example, a frozen selection B and a later working edit C are both retained; committing B after restoration leaves C available for further work. Restore retries use a receipt in the restored database so a late retry cannot erase changes made after a successful restoration.

An exploration workspace may name a model at an exact Git commit or in the working tree, independently of the older SQLite release catalog. Complete backup must validate that workspace against the real package at its dataset ID and requested revision, including its historical head/comparison references and selected view. A forty-character identifier is not sufficient evidence, and the current HEAD must not substitute for a saved older revision. Backup uses a trusted package resolver under the existing mutation barrier; restore resolves against the candidate's own repository and model files before replacement. Missing commits/models, mismatched dataset identities, malformed workspaces and dangling historical references fail closed without changing the active library. SQLite-only historical releases retain their existing validation path.

A candidate that carries an owned Git repository must already resolve HEAD to an existing commit through the same isolated Git runner used by the repository. Admission applies even when no exploration workspaces exist or all saved workspaces name SQLite releases. A symbolic HEAD file, another branch or a preserved tag is not a substitute for its missing target. Candidate validation must never repair that state by creating an initial commit or ref. Creating the first commit remains valid for an ordinary new library; non-Git backups and existing SQLite-only restoration retain their established paths.

The macOS recovery case includes committed acquired sources and their saved previews, a Git-qualified exploration workspace, staged research B and later working research C. The user selects a new destination through the native Save dialog, creates a complete backup, and restores it into an isolated empty library. Both the desktop service runtime and the ordinary installed journey must retain the exact workspace revision and B/C distinction. An incomplete write leaves no new destination file, preserves the usable source library and permits a retry; component or source-only tests do not establish installed acceptance.

Older `.sqlite` backups contain only the earlier history library. They do not contain the data-revision repository, research records or acquired source archive. An application with an existing data repository refuses to treat that format as a complete restore. The old service without a data repository retains its SQLite restore route. Legacy conversion into the current working model needs an explicit import workflow; it is not performed silently.

Backups are written only to the destination selected by the user. They contain local research and operational data and are not release/source-publication artifacts. The application runtime and bundled Git executable are installation resources rather than user-library backup contents.
