# Data workspace requirements

Document v0.2.1 · Product scope v0.1 · 25 October 2026 · Proposed implementation contract

This module supersedes the separate schema-first management workflow in PRD v0.3. The existing manager demonstrates persistence and publication mechanics; it does not satisfy the discovery, usability, scale or unified editing requirements below. This is a design specification, not a claim of implemented capabilities.

## Purpose

A history learner should be able to find material outside the installed collection, understand what it can establish, adopt it into a local working model, review a difference, commit selected changes and continue exploring. Importing, adding a historical state and correcting a claim must share one workspace. Users should not have to understand internal tables, write JSON, obtain external numeric IDs or assign dataset revision identifiers before starting.

The initial audience has some programming or AI-tool experience. RDF, SPARQL, Git internals and the GitWorld schema are not prerequisites. English and Simplified Chinese cover the full workflow. Historical content remains English-first with explicit fallback.

Users must complete these journeys in the installed desktop application without Codex, an LLM, developer scripts, hand-written JSON or backstage data repair. Search means name/identifier lookup and explicit supported filters, not arbitrary natural-language question answering. Reusable mappings, query-driven views and validation are deterministic application features. Human review happens through the application. The [data model](data-model.md) defines assertions, objects, states, continuity paths and views, and separates source acquisition from historical interpretation.

## Model editor navigation refinement

The existing model-package editor remains an advanced local tool. A user must be able to identify its current section and distinguish editing model packages from finding historical sources.

- Keep the macOS title bar for the editor title, return action and Guide. Place local navigation at the upper left of the content area, with a visible blue selected state and `aria-current` for the active section.
- Group **Drafts and releases** under Model packages, show **Model objects** and **Publication review** when an applicable package is open, and name the existing source configuration **Met source configuration**. It only configures the implemented Met request workflow.
- Place refresh/import actions and full-library backup/restore in a separate operation band above the active content. They are actions, not sections, and must not receive navigation selection styling.
- Offer the real workbench **Find data** entry only when its navigation callback is connected. Moving there uses the same unsaved-form guard as returning from the editor. Re-selecting the current section keeps the form intact.
- Preserve object-form, auxiliary-form, backup/restore and publication safeguards, title-bar drag behavior and the Guide entry. This limited refinement does not expand source support or change data operations.

Acceptance for this refinement: the active section is clear in both locales; Met configuration is named accurately; every existing operation remains reachable; changing section or leaving for Find data preserves the existing dirty-input decision; and import/backup/restore remain visually distinct from navigation. Rendered macOS review is required before accepting the layout; a type check alone does not establish it.

## One workspace and one repository HEAD

The editing loop is **working changes → staging → commit → inspect the result**. A commit records the staged content and advances HEAD; when attached, it also advances that branch. Detached editing must be explicit and offer a new branch, never commit to an unrelated branch silently. A stable release or export is an optional distribution step, not a prerequisite for every local edit. Committing locally does not upload to a remote service.

The default change list puts edited historical objects, research and model records before supporting sources and mapping metadata. Apply this stable order before filtering and pagination, so a large set of import baselines cannot hide the user's records on later pages. Keep all changed paths inspectable. Object import baselines, active field catalogs and catalog baselines have distinct structured roles and localized subtitles; two related metadata files must not appear as indistinguishable records. Dependency review still includes the exact supporting files, and staging/commit counts retain their file-based meaning.

Historical time and editorial time are distinct. Adding three states dated 843 can be one editorial commit made today. Correcting a source for an existing state creates a new editorial commit without inventing another historical event. Historical parent/integration/influence relations are domain content, distinct from editorial commit ancestry.

Use one unqualified HEAD, belonging to the data repository. Standard `git` concepts and commands manage that repository. Historical preview, fixed state and comparison remain separate domain operations:

- `history show`: preview an object without changing a fixed historical reference.
- `history checkout`: fix a historical state together with its repository revision.
- `history diff`: compare two independently revision-qualified historical states.

Browsing scope, preview, checked historical state and A/B remain independent. Commit advances the current editing workspace and makes new content visible; existing fixed historical references retain their original revision until explicitly changed. Commands have the same meaning in every panel. Old prototype commands that used HEAD for a historical state need explicit migration guidance, never silent reinterpretation.

External Git clients are not a release requirement. A standard Git implementation may be embedded if it improves reliability and extension. Compare available implementations through a focused integration experiment before assigning authoritative ownership of the index, commit graph and refs. SQLite may continue to own query indices, acquisition jobs and caches. Installed users must not need a separately installed Git or developer runtime.

## Discovery and source strategy

Wikidata is the first planned discovery and structured-claim source. It provides stable entities, names, identifiers, time-qualified statements and references, with several access paths rather than one unlimited query endpoint. Its structured data is CC0; that does not extend to arbitrary linked text or media. Use task-sized local subsets, not a mandatory full dump. [Official access methods](https://www.wikidata.org/wiki/Help:Data_access), [downloads and licensing](https://www.wikidata.org/wiki/Wikidata:Database_download).

Wikipedia supplies context and versioned evidence-reading links. Its article revisions are modern edits, not ancient events; article text and Commons media have separate reuse requirements. Pleiades is a candidate for ancient-place reconciliation. Met remains useful for material culture, with a discoverable acquisition interface instead of a required list of object IDs. Source count is not an acceptance metric. [MediaWiki revisions](https://www.mediawiki.org/wiki/API:Revisions), [Pleiades downloads](https://pleiades.stoa.org/downloads), [Met API](https://metmuseum.github.io/).

The first source feasibility check retrieved full statements for four Wikidata entities and a bounded, type-and-date query returning twenty treaty records. This established discovery beyond preset IDs; it did not establish comprehensive coverage or bulk-ingestion readiness. Competing dates, missing references, absent labels and differences between descriptions and structured dates must remain visible.

A source record is not automatically a historical state. A person, place, artifact or encyclopedia entry can be searchable material without becoming a fabricated branch. Date precision, calendar, competing statements, qualifiers, references, source revision and statement identity must survive normalization. Current national affiliation, succession properties, object production dates and retrieval timestamps do not directly establish historical ancestry or state transitions. [Wikibase time model](https://www.mediawiki.org/wiki/Wikibase/DataModel#Dates_and_times).

An annual state selection is a query scope, not a request to reduce the source's date precision. Ordinary state values, comparison endpoints, assertion applicability/evidence and source-mapping previews must retain recorded month/day components and distinguish different days within the same year. Use the same bounded date presentation rule across these consumers. Preserve historical/BCE years, possible year ranges, each endpoint's precision/calendar, open intervals and original date text. Localized month names format recorded scalar components; they must not infer a calendar, convert through the host timezone, pad a historical year or correct an invalid date. Show normalized dates in the primary reading path and retain original text through progressive disclosure, deduplicated within an assertion's date evidence. Acceptance must exercise day-precision values and applicability in both locales through ordinary state, comparison and Evidence actions, including same-year different-day and unspecified-calendar cases.

## Required journeys

The initial bulk collection entry offers trusted public datasets alongside entity-name discovery. Cliopatria uses a pinned official release for provisional polity/geography observation frames; its dates do not define canonical polity lifetimes and reused external IDs do not merge objects. Pleiades uses its official comprehensive JSON dump for ancient place/name/location attestations. A learner chooses supported source-name/date filters and a bounded batch, sees its actual record/object/dated-assertion coverage, then previews and adopts through the same object tree and Changes workflow. Download checkpoints, cached source revisions, cancellation and a next-batch cursor are retained locally. The interface never accepts arbitrary provider URLs or requires the learner to construct thousands of IDs. These bulk controls are an implementation requirement, not a claim that the existing entity-search screen already supports them.

Retain every concrete mapping issue for a completed batch and make the complete report available through bounded pages. A preview sample must never be the only saved exception record. Count concrete mapping issues separately from aggregate excluded records: one source record can produce several issues, and Pleiades' aggregate invalid-record count does not supply individual locators. Show the scanned boundary for that aggregate; records excluded before filtering are not presented as query matches. Older checkpoints that retained only a sample are explicitly partial. They can rebuild the report from the same pinned local snapshot and original query, preserving the existing batch and adopted data; changed mapping output, unavailable cache, failure or cancellation cannot silently replace the earlier result. This recovery does not fetch a newer source or review claims automatically.

1. **Expand coverage:** start from a scope or historical question, search by name, preview the actual result boundary and fetch selected material without knowing external IDs.
2. **Add a historical state:** extend a meaningful historical parent, or create a parentless first recorded observation for a subject not yet modeled. A baseline marks the start of recorded coverage, not the subject's origin. Provide time, fields and evidence, inspect the resulting state/graph and commit it.
3. **Correct a record:** edit a claim or source in place, inspect its field difference and inherited downstream effects, commit the reason and retain reproducible older versions.
4. **Refresh a source:** rerun a saved task, distinguish unchanged/new/changed/possibly removed records and resolve upstream-versus-local conflicts without overwriting research.
5. **Exchange and recover:** import ordinary CSV through column mapping or a structured data package; export and restore content, evidence, commits and unfinished work locally.

### Direct object additions and corrections

Provide ordinary Add claim and Correct claim controls for a selected object, plus an entry for a new object. A claim is a source-backed assertion; observations name the historical state observations produced from those assertions. The user chooses a named field and a structured value, historical applicability and evidence. Entity values use name search with explicit selection. Fields and types reuse the collection's display catalog; users do not enter object IDs or schema JSON. A new object's first dated claim establishes recorded coverage, not its historical origin. This complements automatic source mapping rather than requiring every imported row to be authored manually.

Corrections edit the current working object, regardless of the historical revision being viewed. Display that distinction before saving. Preserve the original source snapshot, import baseline, untouched qualifiers and value metadata. An existing value that the form cannot represent stays intact unless the user explicitly replaces it. Evidence can reference an existing source header or a new HTTPS citation with a title and locator. The service records the local amendment and its reason without attributing the changed value to an unmodified upstream record. New work starts unreviewed; marking it reviewed is an explicit choice.

Saving validates the exact object content hash and repository HEAD, writes a coherent working increment idempotently and returns the affected object/claim. It does not stage or commit. The ordinary state, comparison, evidence and Changes paths consume that increment; unreviewed applicability remains explicit. Incomplete forms are recoverable local input, not valid historical data, and closing the editor does not silently save a domain correction. Discard draft requires explicit confirmation, removes only the unfinished form and returns to exploration. An operation with an unconfirmed save result must be checked before the form can be discarded. Conflicts retain the input and require review against the current working record before retry.

Research evidence remains inspectable without consuming the document. Show a compact bounded set of evidence rows, the full attached count and explicit expansion; details and removal belong to the expanded row. Preserve all saved evidence, including older records, and never use visual folding to conceal an incorrect attachment set. References attached from a comparison must identify the actual supporting or possible assertions of its fixed endpoints. Research scope differences show exact distinct object/field counts and available semantic labels; unresolved identifiers belong in details, with no inferred object names.

Research input and saved research records have separate lifecycles. Leaving a new or edited investigation retains its raw recoverable input, including an empty question or incomplete dates; it does not create or update a working record. Explicit Save validates the question, dates and references with the expected content hash. A successful recovery-buffer write must be durable before navigation or closing proceeds; a failure keeps the input visible and offers retry. Reopening resumes that input and retains any save/conflict error until it is resolved. A single active recovery buffer must not be silently replaced when opening another record or starting a new investigation: offer Keep editing, Save and continue, or explicitly confirmed Discard and continue. A separate Discard draft action also requires confirmation, removes only unfinished input and leaves an already saved working record intact. The same policy applies to new drafts and edits of existing records; no placeholder title or unwanted saved record is required to cancel an investigation.

Source presentation must remain usable for bulk-mapped objects. Prefer the source's supplied title; an untitled source falls back to its registered provider name, or the literal provider name when unknown, rather than an opaque external identifier or content hash. Object details may fold source headers into a document group only when the exact document URL, provider, source revision and supplied title metadata match within the same data-repository revision. Distinct revisions or titles remain separate. This is a presentation grouping, never a provenance merge: every original source ID, external identity, hash, retrieval/adapter metadata and associated evidence locator remains inspectable. Field-level evidence continues to identify its exact source record and fixed data revision. These rules apply to all providers and imported objects without subject-specific branches.

## Acquisition and local operation

Opening or refreshing a source view must not reclaim a later workspace. Leaving invalidates pending view initialization and record/job reads; their late responses cannot reopen the source view, redraw a newer editor or replace its focus. Acquisition and accepted imports may continue in the background, retaining their durable results and truthful progress. A completed background job becomes available in saved material without automatically selecting it over a later investigation. Reopening sources performs a fresh view read and retains the current navigation context.

### Wikipedia source reading

The [bounded Wikipedia acquisition and mapping contract](source-bindings-prd.md#bounded-wikipedia-acquisition-and-mapping-increment) is consumed inside the existing Sources workflow. Search offers a source choice, with English Wikipedia accepting an exact page title and optional revision; Saved material lists its durable jobs and fixed snapshots. The user inspects a table, selects a named versioned profile and its actual source columns, previews the scope/claims/exceptions/vocabulary against one library HEAD, and explicitly adopts into working data. Existing Public datasets and Imports and matches retain their roles. No additional top-level activity, hardcoded historical page or arbitrary mapping-code editor is introduced.

Recover page input and bounded column choices locally; preserve the source and accepted import receipt in their existing durable stores. Source revision, profile version and editorial repository revision remain distinct. Changing a source, profile, columns or calendar requires a new preview. Cancellation and retry preserve acquired material; accepted partial adoption recovers through Imports and matches without fetching or remapping. Unknown source rights, unsupported dates and missing translations remain visible. Before acceptance, operate both supported profile families on different compatible tables, review actual exceptions and date/applicability counts, adopt, inspect the new ordinary state/evidence paths, commit, restart and resume an interrupted import through the installed UI. Backend or design-state evidence alone does not pass this journey.

A Wikipedia job retains the provider's Retry-After deadline in its durable attempt receipt. Resuming before that deadline returns the saved partial result without another provider request or extending the deadline; this also applies after restart. Once the deadline passes, an explicit retry resumes the same pinned source revision. Completed snapshots remain reusable without network access. Saving a retry interval is not evidence that the service enforces it; controlled protocol tests must check both sides of the deadline.

New column drafts retain the source's unspecified calendar unless the user explicitly selects Gregorian or Julian; an unspecified choice omits the mapping request's calendar override. Previously saved explicit choices remain unchanged. The preview must preserve the returned month/day, precision, range and calendar for review rather than reducing day-precision applicability to a year-only interval. A missing page or requested source revision explains that result and retains an Edit request path. Before enabling adoption or recording preview progress, the response must match the requested acquisition job, source hash, exact selection and prepared base. Complete mapping exceptions are available through bounded reads of that same saved preview; page failures keep the current report page and choices, and late or mismatched pages cannot replace another preview's report.

Search and filtering expose only actual provider capabilities. Distinguish upstream filters, local filters, unknown dates, missing coverage and truncated results. A sample or LIMIT response is not a complete collection count. Users can save and modify their scope; no fixed example list or source-specific UI branch should be required for a new subject.

Persistent jobs retain source/query/mapping versions, cursors or checkpoints, retrieval time, completed batches, raw hashes and failures. Support bounded fetching, cancellation, pause/resume, restart recovery and retry of failed items. Respect current service limits and Retry-After. Large offline tasks use appropriate file/dump ingestion paths. Previously adopted content remains usable offline; remote discovery and refresh honestly require connectivity. [Wikimedia usage policy](https://foundation.wikimedia.org/wiki/Policy:Wikimedia_Foundation_API_Usage_Guidelines), [WDQS limits](https://www.mediawiki.org/wiki/Wikidata_Query_Service/User_Manual#Query_limits).

Keep original records, normalized claims, local overrides and committed model content distinct. Stable object matching uses provider plus external identity, not a display name or upstream revision. Revision/hash identifies an input snapshot for comparison across updates; it does not create a new entity identity. Cross-source identity matches need inspectable evidence. Preserve a baseline for three-way updates: previous source value, incoming source value and local value. An upstream deletion is a reviewable change, not proof that a historical fact never existed.

## Changes, staging and commit

Changes has a compact Working/Staged switch and a single filter/selection group. Its commit editor opens explicitly and can be closed without discarding the recoverable reason; a recovered reason or unresolved commit attempt opens it again. The frozen count, reason and contributor identity appear together. Advanced branch, revision-log, checkout and revert operations remain reachable outside that editor. Closing a panel does not change the staged tree or authorize a commit.

The Changes view groups meaningful object changes, with before/after values, evidence, unresolved issues and affected historical states. Advanced raw properties and mapping diagnostics remain available. Reusable mapping rules support batch adoption and an exception queue; users should not repeat the same decision in hundreds of forms.

Staging freezes content. If a user stages A→B and then edits the working value to C, the commit contains B and B→C remains unstaged afterwards. Selecting a live object is insufficient. Required sources/identities/parents must be staged together or produce a clear dependency error; do not silently stage unrelated work.

A commit preview identifies both directly changed objects and inherited downstream changes. The commit operation revalidates the exact staged tree and expected base/ref before recording it atomically. No half-publication or duplicate retry may become visible.

Structurally valid local material with source identity and an explicit unreviewed status may be committed as research. This neither confirms a historical claim nor authorizes public distribution. Structural errors cannot enter a runnable model; unreviewed claims cannot masquerade as confirmed historical states. Public distribution adds a separate evidence and rights gate; personal backups are not public distribution. Raw form buffers remain recoverable working input, not falsely valid committed data.

## Implementation order

### UED06 backend bridge

Model catalog/read operations use the editorial working tree or an explicit actual commit OID. Their envelopes retain the authored package revision separately from the repository revision, content hash and base HEAD. A legacy SQL revision remains readable for compatibility, but is not the default model catalog or a substitute for a Git commit. A shape-valid imported package may remain an editable SQL draft; only a package that passes the applicable draft/publication validator enters `models/<dataset-hash>.json`. Reviewed publication produces a working change and does not stage or commit automatically. Writes compare the reviewed HEAD and previous model hash, retain durable retry receipts and must not overwrite later working edits when replayed.

The global bounded command service routes `git` operations to the same repository handlers used by Changes. `history` commands and GUI intents carry an explicit model or object target and revision. A historical checkout or comparison requires an actual committed revision; working previews remain available. Legacy model query operations remain readable, while conflicting global aliases return structured migration guidance. Model history retains its graph operations; object inspection exposes its actual state, observations and evidence without inventing ancestry. No command selects its meaning from the current page or executes a system shell.

Terminal results offer **Open result** only when the existing workspace can open the result's historical view, scope, membership plan or Changes review. A repository refresh is not a view action: `git status` keeps its specific **Review changes** action, while `git log` displays its entries directly; neither also offers Open result. Repository branch, switch and checkout results likewise remain direct output. The six repository operations that already open Changes—add, unstage, diff, commit, revert and abort-revert—retain that result action. Historical results with no view effect do not advertise one. Opening a result does not rerun the command or replace the user's next command draft; late command completion still cannot navigate or steal focus from a newer investigation. Verify both locales, direct-output and actionable result types, explicit result activation and retained input/context.

Completing an unrelated object, state or evidence read must not interrupt terminal input. While the terminal remains visible, retain its connected form/input nodes, draft, focus, selection and in-progress text composition across workspace redraws; unchanged terminal content needs no replacement. Enter must still submit without requiring the user to refocus or wait for the historical view to finish loading. If the user has moved to another input or investigation, a late response must not reclaim terminal focus. Acceptance gates the fixed object's four reads, focuses and edits the terminal, then releases the reads and verifies the same input/caret and ordinary Enter submission, with contrasting focus-change and composition cases in both locales. Component DOM evidence and installed keyboard/IME acceptance remain distinct.

Historical command errors separate candidate identity from executable recovery. `candidates` and replacement syntax are explanatory data, not command buttons. Typed recovery actions retain the exact model/repository revision and stable candidate ref or both independently qualified endpoints. For an ambiguous model ref, offer an explicit Show action for each valid candidate. For `MULTIPLE_COMMON_BASES` or `NO_COMMON_BASE`, offer a double-dot comparison of the original resolved A and B, preserving direction; never choose a base or convert the error into an arbitrary historical checkout. An ambiguity on the B side of a cross-revision comparison is inspected at B’s revision, not the currently open model or A’s revision. Only a complete bounded replacement command may be executable; a bare `CHECKED` alias or a template containing placeholders remains syntax guidance. Selecting recovery fills the full command and does not execute it, move a historical reference or change modern HEAD. The user can edit it and explicitly Run. Acceptance requires the selected command to pass the actual parser/executor, with preserved target/OID, bilingual labels and unchanged pins until execution; native replay remains a separate gate.

Backend acceptance requires mixed model/object staging in one commit, B-stage/C-edit, immutable old model/object references after a new commit, a failed or interrupted model write followed by safe retry, strict command rejection/migration, and bounded bulk unstage with the shared path limit. These checks do not establish installed UED06 acceptance.

The backend bridge is implemented with semantic integration tests covering those cases, complete-library restore and independent model endpoints at different OIDs. Workspace schema migration 3 preserves existing rows while removing the obsolete foreign key to SQL-only publications; trusted service validation checks the actual Git model and each fixed reference before persistence. Repository diffs read exact paths in batches and return bounded pages. Trusted write-progress observers receive only completed/total counts after file and directory synchronization, at most 100 completed paths apart and at the final item; observer failures cannot change the write. An interrupted object/baseline pair is repaired on retry from the exact upstream candidate with both content hashes guarded. Desktop integration, rendered bilingual review and the installed complete journey remain separate acceptance work.

Complete the interaction and version-model review, validate a standard Git integration option, then implement one deep source-to-commit journey. Extend durable jobs, incremental reconciliation, recovery and command parity before multiplying adapters. Preserve useful validation, provenance, transaction and backup infrastructure; replace the default full-dataset CRUD/publication workflow and the automatic artifact-to-branch mapping.

The accompanying [interaction specification](data-workspace-ued.md) defines the design work. Main PRD/UED, Figma, commands, implementation and acceptance evidence must move together; documentation changes alone do not synchronize the product.

## Research contexts and scope navigation — UED 07

The [scope module requirements](scope-workspace-prd.md) define user-created research contexts, explicit whole-batch membership and unassigned material. They extend this workspace without adding an activity or a country-specific page. Contexts are versioned navigation metadata in the same Git tree, separate from historical objects, assertions, events and date statistics.

Assigning a successful import to a context is an independent, reviewable working change. It neither modifies the facts-import receipt nor rolls back adopted facts on failure. Preserve the active investigation; View context is explicit navigation. Historical checkout/A-B remain fixed independently of context/query revisions. The module specifies CAS, command parity, backup/compatibility and acceptance; its production implementation remains incomplete.
