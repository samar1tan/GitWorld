# Project website

The GitHub Pages site is a maintained product entry point. It introduces the local desktop learning workflow, connects examples to shipped capabilities, and leads visitors to the current public preview or source. Website examples do not establish complete historical coverage or installed acceptance.

## Three historical investigations

Both languages offer the same three selectable cases over existing product-authored records. Case selection is independent of language. The initial case is China/Japan in both languages, preserving the established Chinese entry while keeping language parity.

| Case | Question and Git modeling connection | Required historical boundary |
| --- | --- | --- |
| Frankish partition | Follow shared Carolingian records into West, Middle and East Francia at Verdun; compare sibling states against their common past. | Splits are modeled historical continuations, not modern countries projected backward. Condensed ancestry must be identified. No new merge or territorial boundary is invented. |
| China and Japan | Compare Chang’an around 700 with Nara in 710, then follow the Japanese court's six capital observations through 794. | Chang’an is an approximate planning observation. A labeled dashed influence arrow is separate from solid continuity edges; Japan is not a child of Tang. |
| Abbasid court | Follow Baghdad in 762, Samarra in 836 and the return to Baghdad in 892. Compare matching residence values alongside changed recorded context. | Equal endpoint values do not erase intervening history. The return is a later record on the same path, not a graph cycle, reset or claim that an entire society reverted. |

Use the existing curated history dataset and the same domain snapshot/comparison engine as the desktop app. The website supplies bounded read-only examples; it does not edit a library, call an LLM, simulate successful desktop commands or introduce new historical records. Original bilingual case explanations accompany claim-level evidence links. The sources' original titles remain identifiable.

## Interaction and layout

- Retain the canonical desktop logo, optical small favicon, local fonts, source link, language switch and current preview download. Do not change release-validation policy or manufacture verified release metadata.
- Separate the short product introduction from one shared case workbench. Three clearly named case tabs remain visible; there is no automatic carousel. Each shows its period, specific question, modeling insight and selected-record graph.
- Graph nodes are actual keyboard-operable record buttons. Selecting a node updates its record title, historical date, branch, recorded fields and evidence. Selection does not change the comparison endpoints.
- A and B choose any illustrated record in the active case. The comparison shows meaningful fields, distinguishing equal, changed and unknown values using the domain engine. Switching cases supplies that case's useful initial record and pair. Switching language preserves the active case, selected record and A/B IDs.
- Explain condensed parent edges, approximate dates and influence where relevant. Spacing is not an elapsed-time scale. Do not draw an edge merely because two records have equal values.
- Keep three desktop operations and their qualified `history` commands aligned with the active case. Commands are instructions for the installed terminal; the website does not pretend to execute an editorial Git repository.
- Expose case identity in `?case=` and locale in `?lang=zh-CN`. Invalid case values select the documented initial case. Language and case changes use `replaceState`; reload restores them without adding redundant history entries.
- Desktop uses a readable graph/detail arrangement. Narrow layouts stack the selected record and comparison. The graph may scroll within its labeled keyboard-focusable region; the page must not overflow, squeeze essential labels or hide locale/case controls.

## Evidence and content

Use the reviewed seed's source metadata, historical IDs, typed relationships and field provenance. The new website code and narrative are original project contributions. Cite third-party historical sources instead of copying their prose or illustrations. Inherited fields remain inherited model values, not new historical confirmation. A missing field remains unknown.

The Abbasid example is supported by the [Metropolitan Museum's Abbasid overview](https://www.metmuseum.org/essays/the-art-of-the-abbasid-period-750-1258) and the [Qatar Museums Samarra account](https://qm.org.qa/en/stories/all-stories/collection-highlight-abbasid-stucco-panel/), already cited in the shipped seed. This iteration does not broaden the data collection or app release scope.

## Acceptance

- All displayed nodes exist in the shipped dataset; continuity and influence edges match their actual modeled relations. Test condensed ancestry and complete Japanese capital coverage.
- All three cases use actual snapshot/comparison logic. Check Frankish sibling differences/common base, independent Chang’an/Nara paths, and Abbasid equal residence with changed context and retained Samarra history.
- Both locales present equivalent facts, stable IDs, evidence, controls and desktop command targets. Operate case/node/A/B selection, repeated language switching, keyboard access and direct/reloaded links.
- Inspect actual rendered desktop and narrow/mobile layouts in both languages. Check action wrapping, graph/node labels, focus, comparison readability and page-wide overflow. Record actual operations separately from source tests.
- Verify the deployed page, assets, language/case state and preview link after publication. Keep `site/release.json` null until the separate full release gate passes; no new desktop acceptance is implied.

## Maintenance

Maintain the website alongside the app, README and Issues. Keep affected requirements, case content, source mappings, downloads and localization aligned. Link the fixing PR and deployment to the focused website issue; do not resume unrelated roadmap work.
