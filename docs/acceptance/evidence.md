# Acceptance evidence

Release acceptance combines ordinary installed journeys with separately identified engineering evidence. Keep all D, M, J, S, N and C requirements; this distinction does not waive a required result. Record each required portion and leave the requirement unpassed if any portion is incomplete. A structurally valid receipt is not proof that its observations are sufficient.

Run the visible user journeys on the exact final installer, recording its hash, build and source revision, the data revisions, actions and observed results. This includes C01–C12, M13, real acquisition of at least 1,000 source records with usable adopted assertions, independent China/Japan questions, conflict decisions, frozen staging with later edits, research, restart, complete restoration into an empty target, offline exploration and both locales. Only shipped controls, bounded commands and documented file selection count. Developer edits, generated answers and hidden state injection cannot supply these results. Earlier package observations retain their own artifact identity.

Use isolated, deterministic engineering regressions for precise fault, protocol and compatibility boundaries. Bind them to the final source and the tested runtime and bundled Git. Identify synthetic inputs and controlled HTTP responses explicitly; never call these installed observations or inject them into the installed investigation library.

| Mixed requirements | Engineering portion, in addition to the installed user journey |
| --- | --- |
| D04, M06–M08, N06 | Exact interrupted-write and process-death boundaries, compare-and-swap interleavings, durable retry identity and preservation of later edits. |
| M08, J03, J06 | Controlled 429/Retry-After, upstream busy, timeout and cancellation; restart retains fixed source/preview/operation identity without duplicate adoption or premature guidance progress. Do not deliberately overload a public provider to obtain a real 429. |
| D06, D12, N07, S05 | Supported old-schema migration and rollback; unsupported or corrupt metadata/container rejection; pending receipts and partial operations preserved across complete backup and restore. |
| D07–D08, D11, S06 | Rare graph extremes, privilege/runtime boundaries, package integrity, rights and privacy checks. These supplement actual GUI/command interaction; they do not establish it. |

Normal cancellation, a malformed archive or a successful restart proves only the boundary actually exercised. It does not establish an exact crash window, unsupported-schema handling or pending-operation recovery. Preserve failed and unrun results. Agent operation, engineering tests, clean-machine testing and human learning studies are different evidence and must be reported as such.
